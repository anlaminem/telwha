Estrategia short en listados de Bybit: prueba de TP/SL y del momento de entrada

Caso sobre un simulador de estrategia short en nuevos listados de Bybit: cómo comprobar una idea mediante velas históricas, grid search y patrones temporales, en lugar de un muy seguro «me parece que sí».

Un nuevo contrato aparece en el exchange, en los primeros minutos todo vuela en distintas direcciones y luego una parte de los participantes recuerda la gestión del riesgo. Esa breve ventana “post-listing” se convirtió en el objeto de este caso.

La tarea parecía estándar para cualquier producto con lógica de mercado: formalizar la hipótesis, reunir los datos, construir el simulador, ejecutar los parámetros y ver si existe una ventaja estable. En este caso concreto, se trataba de operaciones short sobre confirmed listing events de Bybit con riesgo fijo y una lógica clara de TP/SL.

Si una estrategia no supera un backtest simple, no tiene posibilidades de sobrevivir en un entorno donde las decisiones se toman a velocidad de producto, no de presentación.

Para la prueba utilicé diez confirmed listing events de contratos USDT. Para cada lanzamiento se cargó una ventana de datos de un minuto: desde 18 horas antes del listing hasta 10 horas después. La parte pre-listing se conserva en esta etapa como contexto para un análisis futuro de patrones, mientras que la parte post-listing se usa directamente en la simulación de la operación. Los datos se obtuvieron a través del endpoint Bybit V5 Market Kline, que devuelve historical candles para un símbolo, un intervalo y un rango temporal determinados.

El momento del listing se define como entry_dt, y el marco de datos se define como start_dt y end_dt. Como resultado, el modelo tiene un contexto adecuado antes del evento y un recorte completo después de él.

Code Ventana de datos alrededor del listing ▾ 
for symbol, entry_str in allpairs:

La función de obtención de velas convierte los timestamps a milisegundos, hace la solicitud al API y devuelve un DataFrame ordenado. No hay datos “sintéticos”, solo lo que realmente existe en el historial del instrumento.

Code Obtención de historical kline ▾ 
def get_klines(symbol, start_dt, end_dt, category="linear", interval="1"):
    start_ts = int(start_dt.timestamp() * 1000)
    end_ts = int(end_dt.timestamp() * 1000)

    resp = session.get_kline(
        category=category,
        symbol=symbol,
        interval=interval,
        start=start_ts,
        end=end_ts,
        limit=1000
    )

    rows = resp["result"]["list"]
    df = pd.DataFrame(
        rows,
        columns=["timestamp", "open", "high", "low", "close", "volume", "turnover"]
    )
    df["datetime"] = pd.to_datetime(df["timestamp"].astype("int64"), unit="ms", utc=True)
    return df.sort_values("datetime").reset_index(drop=True)

Luego viene el simulador de la operación. La entrada comienza con la primera vela no anterior a entry_dt, y después se comprueban secuencialmente el TP, el SL y el timeout.

El esquema es intencionalmente minimalista: un solo punto de entrada, un tamaño de riesgo fijo y un recorrido lineal vela por vela hasta que se active el TP/SL o termine el escenario. Este marco permite interpretar el resultado rápidamente y no ocultar la lógica bajo capas de complejidad.

Code Simulación básica de una operación short ▾ 
def simulate_short_trade(df, entry_dt, entry_amount=100.0,
                         tp_pct=5.0, sl_pct=4.0, duration_min=600):
    mask = df["datetime"] >= entry_dt
    if not mask.any():
        return None

    entry_idx = mask.idxmax()
    entry_price = float(df.loc[entry_idx, "close"])
    pos_qty = entry_amount / entry_price

    tp_price = entry_price * (1 - tp_pct / 100.0)
    sl_price = entry_price * (1 + sl_pct / 100.0)
    end_idx = min(entry_idx + duration_min, len(df) - 1)

    for i in range(entry_idx + 1, end_idx + 1):
        high_i = float(df.loc[i, "high"])
        low_i = float(df.loc[i, "low"])

        if low_i <= tp_price:
            return {"PnL": (entry_price - tp_price) * pos_qty,
                    "closure_type": "TP"}
        if high_i >= sl_price:
            return {"PnL": (entry_price - sl_price) * pos_qty,
                    "closure_type": "STOP"}

    last_close = float(df.loc[end_idx, "close"])
    return {"PnL": (entry_price - last_close) * pos_qty,
            "closure_type": "TIMEOUT"}

Sobre esta base se añadió una versión ampliada con varios niveles de TP, salidas parciales y promediación. Allí donde el producto necesita una lógica más flexible de gestión de posición, esos son precisamente los bloques que cambian primero.

La siguiente capa es la selección de parámetros. En lugar de discutir si un TP del 5% “suena más sólido” que uno del 4%, se ejecutó un grid search: varias opciones para el primer y el segundo TP, varios niveles de stop loss y varias estructuras de distribución de la posición, incluidos escenarios de full exit y split.

El enfoque es estándar para cualquier módulo de backtest: definir una cuadrícula de parámetros, ejecutarla sobre la misma muestra y solo después evaluar qué tiene sentido trasladar a producción.

Si el producto necesita un “modo experimento”, este es el punto más cómodo para conectar cuadrículas alternativas de parámetros y compararlas en nuevos lotes de listings.

En la muestra de 10 listings, el mejor resultado provino de una configuración simple: TP levels = [5, 6, 12], TP shares = [1.0, 0.0, 0.0], stop loss = 4%. Es decir, una salida completa en el primer TP resultó más eficaz que cualquier estructura split.

Las cifras finales para esta configuración fueron: resultado total de 14.95 USD con un riesgo fijo de 100 USD por operación, resultado medio de 1.50 USD por trade, win rate del 60% y una estructura de cierres de 6 TP, 4 SL y 0 timeout. Para una muestra pequeña, son valores modestos, pero suficientes para distinguir una hipótesis viable de una puramente emocional.

También se calculó por separado el momento de entrada. La ventana más débil en esta muestra fue 04:00 UTC; la más consistentemente positiva fue 06:00 UTC. Para un producto, esto da una señal simple pero útil: el tiempo es un candidato válido para un filtro adicional de riesgo, no solo un parámetro decorativo.

Qué aporta esto al producto

Desde la perspectiva de la arquitectura de la solución, el resultado puede describirse así: la lógica base short funciona con TP del 5% y SL del 4%, salida completa en el primer TP y un filtro temporal que favorece las 06:00 UTC y obliga a tratar con más cautela las 04:00 UTC. Se trata de un conjunto transparente de reglas que es fácil trasladar a un producto, monitorizar en una muestra más amplia y, si hace falta, adaptar a otro universo de instrumentos.

Para los equipos que construyen sus propias estrategias o servicios de mercado, no solo importa la configuración concreta, sino también el enfoque en sí: una hipótesis formulada con claridad, una conexión explícita con los datos del exchange, un backtest con una cuadrícula controlada de parámetros y métricas de salida legibles. En esta estructura pueden cambiar los instrumentos, los horizontes y el universo, pero la mecánica de validación seguirá siendo estable.

  • Base: un simulador short sobre velas históricas de Bybit con un control correcto de TP/SL.
  • Conclusión: una salida completa simple en TP1 mostró un mejor comportamiento que las salidas split en el conjunto de prueba de listings.
La verificación formal de una hipótesis no garantiza una estrategia perfecta. Garantiza una cosa: dejas de pagarle al mercado por decisiones que podían haberse filtrado ya en la etapa del notebook.
